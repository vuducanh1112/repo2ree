# 0005 — Ship a POSIX shell reproducer in every bundle

- **Status:** accepted
- **Date:** original date unknown; retrospectively recorded 2026-08-11
- **Decision owners:** repo2ree maintainers

## Context

An archived REE must remain usable by someone who has the bundle but does not
have repo2ree, its Python packages, its API, or a running workbench. Requiring
the service that created an artifact in order to execute it would make
repo2ree itself another live dependency in the artifact's reproduction chain.

The bundle already carries the stable ingredients of execution: source or a
source origin, the author's overlay scripts, the REE manifest, recorded
experiments, and optionally a sealed runtime. It needs a portable entrypoint
that composes those ingredients into the same major reproduction phases as the
workbench.

## Decision

Generate a deterministic POSIX `sh` reproducer when core assembles an REE
bundle. Every draft and sealed bundle carries:

- top-level `run.sh`, which orchestrates reproduction;
- `ree/acquire_source.sh`, which extracts the bundled snapshot or fetches the
  recorded origin and attempts to verify its SWHID;
- `ree/materialize_workspace.sh`, which resets and assembles the workspace from
  upstream plus overlay;
- `REPRODUCING.md`, which documents the entrypoint and prerequisites.

`run.sh` exposes the main reproduction phases: acquire source, materialize the
workspace, build the runtime, test activation, run a named experiment, and run
the entire sequence. It can also re-run a declared verify script against
outputs already in the workspace.

The generated shell orchestrates rather than re-creating project behavior.
It invokes the author's sealed build, activation, experiment, and verify scripts
from the materialized workspace. It delegates acquisition and materialization
to the same generated scripts used in the workbench. The shared reproduction
command registry supplies the common CLI verb names and summaries so the
executor and bundle entrypoints do not develop separate vocabularies.

The bundle therefore requires no repo2ree installation to reproduce. It still
requires a POSIX shell, archive and source tools where applicable, and whatever
runtime the author's scripts declare, commonly Docker.

## Alternatives considered

- **Require repo2ree or `repo2ree-exec`.** This keeps one Python orchestration
  path but makes a compatible repo2ree installation and its dependencies part
  of every future reproduction.
- **Ship a Python reproducer.** This would reuse more application code but adds
  a Python interpreter, package installation, and version compatibility to the
  baseline requirements.
- **Ship instructions only.** A prose recipe leaves command order, failure
  handling, workspace reset, runtime reuse, and experiment selection to each
  reader and cannot serve as an executable acceptance path.
- **Ship only a container entrypoint.** This assumes the bundle's outer host can
  run the chosen container substrate and makes inspecting or adapting the
  orchestration harder. Author scripts may still choose containers for their
  own runtime behavior.
- **Use one generic script that interprets `ree.json` at runtime.** Parsing JSON
  portably would require another tool such as `jq`. Generating the registry and
  paths at bundle time keeps the runtime baseline to POSIX shell and ordinary
  filesystem tools.

## Consequences

- A downloaded bundle remains executable without the repo2ree service or Python
  distribution that produced it.
- The reproduction path is inspectable as plain text before the user runs it.
- Equal inputs produce equal generated bytes, preserving deterministic bundle
  inventory and seal hashing.
- The bundle captures resolved source identity, script paths, experiments, and
  sealed-runtime location at assembly time instead of discovering mutable
  repo2ree behavior later.
- POSIX shell becomes a compatibility surface. Generated scripts need syntax,
  quoting, path-safety, failure-propagation, and end-to-end behavior tests.
- The shell does not make an REE hermetic by itself. Network access may still be
  needed for a sourceless bundle or rebuild, and author scripts retain their own
  runtime and platform requirements.
- Executing `run.sh` executes author-supplied code. Recipients must inspect or
  sandbox an untrusted REE just as they would the original repository.
- Some orchestration exists in both Python handlers and generated shell. Sharing
  the command vocabulary plus the acquisition and materialization scripts
  limits drift, while tests must continue comparing their observable behavior.

## Revisit when

Supersede this decision if POSIX shell stops being an adequate portability
baseline, if the bundle format adopts a standard executable-artifact protocol,
or if reproduction semantics can no longer be represented without embedding a
larger interpreter. Preserve repo2ree-independent execution as a requirement of
any replacement.
